AI-as-a-Service Layer

The idea

Universities don't need another AI portal. They need AI capabilities inside the tools students already use: the student portal, the LMS and the mobile app.

The AI-as-a-Service Layer is one backend that any of those apps can call. It offers five capabilities through a single contract: ask, find, plan, recommend and assess. Before a model sees anything, the layer decides what this user may see. Before an answer leaves, it checks every claim against evidence.

The design rests on one decision: a scope is a permission boundary and a personalisation boundary at the same time. The component that decides what a student may see has, in deciding that, already decided what makes the answer personal. There is no second system to keep in agreement, so there is no gap between them for a leak to live in.

Design decisions

Embed what is stable, call what is volatile
The catalogue, regulations and research profiles are indexed. Student records are never embedded; tools read them at request time. A transcript cannot leak through a vector, and erasing a person is a single call.
Permissions travel inside the query
The access filter is part of the SQL that retrieves chunks, not a step applied afterwards. Denied data is never fetched, so there is nothing to scrub.
The planner is not the model
Course recommendations come from a deterministic search over prerequisites, timetable clashes and credit limits, and every rejection keeps its reason. A weaker model writes a worse sentence, never a wrong registration.
The orchestrator is a graph, not a loop
Each capability compiles to a typed plan with declared dependencies, timeouts, budgets and a failure policy. Because the plan is data, it can be printed, reviewed and unit-tested.
Tools over MCP, checked on the server
The same tool registry runs in-process or behind a real MCP server. Permission is enforced server-side, so a tool stays safe even if the code calling it has a bug.
Boring tools, sized honestly
FastAPI, Pydantic and one PostgreSQL store with pgvector hold vectors, keyword search, access lists and traces together. It is built for one engineer to operate, with EU-hosted inference.

ToolsCredit arithmetic, prerequisites, clashes, eligibility; a real MCP stdio serverSynthetic student records
OrchestratorTyped step graph, parallel waves, timeouts, deadlines, budgets, trace and replayNone
Model gatewayRouting by task to a model tier, cost accounting, provider interfaceDeterministic fake provider; LiteLLM adapter written but not exercised
GroundednessCitation check, numbers checked against tool output, lexical entailment, refuse rather than trimNo entailment model or LLM judge yet
EvaluationGolden set with must-call, must-cite and must-plan assertions; CI exit code16 cases

Each stand-in is one swap from production: SQLite to PostgreSQL with pgvector, the hashed embedder to an EU-hosted embedding model, the lexical reranker to a multilingual cross-encoder, the fake provider to LiteLLM, and the token table to OIDC.

What this prototype does not prove yet

  • Retrieval quality. A hashed embedder and a lexical reranker exercise the plumbing, not the semantics. Measuring recall on a real corpus needs the real models, including German compound-word handling, which SQLite FTS5 does not do.
  • Latency and cost under load. Everything runs in milliseconds because the model is a stand-in. The numbers to trust are the token counts and routing decisions, not the wall-clock times.
  • The data platform. Ingestion is a corpus builder over synthetic records. What a real university platform exposes, whether a catalogue, change capture or only a query endpoint, is the one dependency that would change the ingestion design.
