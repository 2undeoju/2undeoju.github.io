What this has to achieve

Objective

App-agnostic · modular · one engineer

Aim 1 · One layer, many apps

The goal's two hardest words are app-agnostic and modular. Taking them literally is what produces a layer instead of an application.

What ships
  • A capability API — five verbs: ask, find, plan, recommend, assess
  • A small embeddable widget for chat and search surfaces
  • Nothing else. No portal, no dashboard, no second login
Why not a destination

A new portal competes with the LMS students already live in. Adoption is the hardest part of any university tool and it cannot be fixed by a later sprint — it is decided the day someone chooses a destination over a capability.

Consequence: the staff workplace and the public site later are a different scope set, not a different build. That is the bonus question answered by the architecture rather than by a promise.

Aim 2 · Correct before clever

A student told they have 12 credits left when they have 24 has been harmed regardless of how good the evaluation harness is.

Three mechanisms, in order of strength
  • By construction — ECTS, prerequisites, clashes and eligibility are tool calls. The model asks a system that knows
  • By checking — every claim entailed against retrieved evidence before the answer returns
  • By ordering — nothing generative ships before the harness that can catch it is live in production

The five requested features are four different kinds of problem: two are pure retrieval, one is arithmetic, two are genuinely generative. Shipping them in that order is the roadmap, and the reason it is not the order of demo appeal.

Aim 3 · One engineer, EU-resident

Three numbers decide every choice in this deck: one engineer, EU only, a thousand students.

Why naming the scale matters

The most expensive mistake available is designing for a scale that does not exist. A 0.1 req/s service needs no sharding, no message bus and no dedicated vector cluster — and each of those would cost a year of the one engineer's attention.

A hyperscaler reference architecture. It would look more impressive on a slide and be the wrong answer for this deployment.

The one idea

A scope is a permission boundary and a personalization boundary at the same time. That is the single design decision the whole layer rests on.

Why it matters

Most designs build personalization as one system and data protection as a second system, then spend forever keeping the two in agreement. Every leak lives in that gap.

Here they are one mechanism. The context resolver decides what a student may see, and in deciding that it has already decided what makes the answer personal.

What follows from it
  • Permission before retrieval — denied data is never fetched, so there is nothing to scrub
  • Personalization is the same code path — no second system to keep in agreement
  • Reuse for staff and public is free — a different scope set, not a different build
  • Erasure stays tractable — every chunk carries a subject, so deletion is a filter away

Hybrid retrieval, the policy gate, the tool boundary, the groundedness check and the three-tier reuse are all downstream of that one idea.

Why scope discipline is the real test here

A self-managed lakehouse — object storage, Iceberg or Delta, a catalogue, Trino or Spark — is routinely a 3–6 engineer, 6+ month build, then a permanent operational load. Proposing it as a side task for one AI engineer is how a proposal loses credibility in the first follow-up question.

A bespoke export, or direct database access. Both couple the AI layer to whatever the platform happens to be today. The catalogue — not the file format — is the portability guarantee.

And if there is no platform yet? The honest answer gets smaller, not bigger: Postgres plus object storage carries a 1,000-student corpus comfortably, and the lakehouse waits for a data team to own it.

When a pod fails
  • Liveness probe fails → kubelet restarts the container
  • Readiness probe fails → pod leaves the Service endpoints, traffic stops arriving
  • Node fails → the scheduler places the pod elsewhere
  • Deploys roll with maxUnavailable: 0, so a bad image never drains the last healthy pod

Proven pattern: this exact probe-and-Helm setup is what I shipped in my own multimodal retrieval and recommender service.

Architecture Overview

Architecture

What kind of architecture is this?

Modular monolith by data, service-oriented by deployment, event-driven only at the ingestion seam, ports-and-adapters inside. None of that was chosen from a catalogue — it falls out of three forces.

ForceWhat it eliminates
0.1 requests/secondThe main reason for microservices — independent scaling — does not apply. Nothing here needs to scale away from anything else
One engineerEvery extra deployable is another pipeline, another dashboard, another way to be woken up. The cost is paid nightly
Permission is a relational joinDatabase-per-service — which is the defining property of microservices, not an optional extra
So it is explicitly not microservices, and that is deliberate

The ACL predicate joins chunks against enrolment and programme membership. Split that across services and the join becomes application-side fan-out: slower, and far easier to get subtly wrong in a way that leaks. A shared database is the anti-pattern that defines microservices — so this is honestly not microservices, rather than microservices done badly.

Nor is it a single monolith

Two things genuinely justify splitting: the GPU workloads need different hardware from the API, and ingestion and evaluation must be off the request path so a slow pipeline never makes a student wait. Those are the only two splits the scale pays for.

Where events belong

Event-driven where producer and consumer have different clocks; synchronous where a human is waiting. CDC events into a queue for ingestion — yes. An event bus in the request path — no: it would add latency and a correlation problem to a flow that is a simple request and response.

And clean architecture is orthogonal

Hexagonal / ports-and-adapters is the internal shape of each service, not a competitor to monolith or microservices. It is what makes the four-seams claim true rather than aspirational: the model gateway, the MCP tool protocol, the catalogue contract and index versioning are ports. Each has an adapter that can be swapped without touching the domain logic.

When this changes: if one capability's traffic diverges by roughly 10× from the rest, extract it. If a second team appears, split on the team boundary — Conway's law wins whether or not you plan for it. Not before either of those.

Seven components, three deployables

The diagram shows logical components because that is what explains the design. They deploy as three images — drawing seven boxes and shipping seven services would be the mistake.

The test for adding a fourth

A new deployable has to earn its on-call surface. It needs either different hardware, a different scaling curve, or a different failure tolerance. “It felt like a separate concern” is a package boundary, not a deployment boundary.

Observability — four pillars, because three are not enough here

The deck claims one engineer operates this at 3am. That claim is only honest if there is an answer to how they would know something broke — and for an LLM system, uptime is the least interesting signal.

Why the fourth pillar is not optional

A conventional stack tells you the service is up and fast. It cannot tell you the answers got worse — and a confidently wrong answer to a student is a 200 OK in 1.2 seconds. Quality is the signal that actually degrades here, so it is instrumented like a signal rather than reviewed like a report.

Cost is a first-class signal, not a finance concern

Every response already carries usage.cost_eur. That makes cost-per-answer a time series you can alert on, and it is how a prompt change that quietly triples context length gets caught in hours rather than at the end of the month.

Instrumentation standard

OpenTelemetry throughout, so the backend stays swappable — the same reason the model gateway exists. LLM calls use the GenAI semantic conventions: gen_ai.request.model, gen_ai.usage.input_tokens / output_tokens, gen_ai.response.finish_reasons, with chat and execute_tool spans.

Honest caveat: those GenAI conventions are still under active development, not stable. Adopting them means accepting some churn — worth it, because the alternative is inventing private attribute names that no tool will ever understand.

What wakes a human — and nothing else does

With one engineer the page list has to be short enough to trust. Four things page: the API is down, Postgres is down, the refusal rate crosses 25% (retrieval has failed, students are getting nothing), or groundedness falls below threshold on a rolling window (the system has started being wrong).

Everything else — a stale index, a rerank failure, a queue backlog, a cost spike — is a dashboard and a morning ticket. Waking someone for a degraded reranker trains them to ignore the pager, which is how the real incident gets missed.

Every response carries a trace_id, and that is the thread that ties it together. A student complaint becomes: paste the id, see the exact scopes resolved, the chunks retrieved, the tools called, the prompt sent, the grounding score. Debugging from evidence rather than from anecdote — which is why this is built in Phase 0, before any feature.

Tier 3 · One store, on purpose

Vectors, keyword index, access-control rows and enrolment all live in one database — because the permission predicate is a join, and a join across two systems is application-side fan-out.

chunks
content, halfvec(1024), BM25 index, as_of, model_version
ACL
scope, subject_id, visibility, entity_ids
traces
every response's citations, grounding score, cost, trace_id
Redis
response cache and the ingest/eval queues — never the source of truth

The cache key is hash(query + subject + resolved scopes). Two students asking the same thing do not share an entry unless their scopes match — a shared cache across subjects is a data leak wearing a performance costume.

~40 GB at 10⁶ chunks

Index RAM-resident, one backup regime, one restore drill, one consistency story. At this corpus size a dedicated vector store buys nothing and costs the joins the ACL depends on.

Tier 4 · The pipeline, off the request path

Nothing here runs while a student waits. A slow or failed pipeline makes answers stale and visibly so — it never makes them slow.

change capture
CDC on source tables, or a content-hash diff if the platform has no CDC
chunk + hash
one record = one chunk, deterministic id, sha256 of the text
embed changed
unchanged → skip · moved → copy the vector · changed → re-embed · deleted → hard delete
index swap
versioned; a new embedding model means blue-green, never in-place
Why hashing is the whole trick

It makes the pipeline idempotent and cheap. Re-running the same window changes nothing; a typical night re-embeds tens of records rather than the corpus. Re-embedding everything nightly costs real money and burns a rate limit for no benefit.

Every chunk carries as_of. A source that misses its freshness SLA raises an alert, and answers drawn from stale chunks say so. This is the direct countermeasure to the stale-answer-library failure that has already harmed students elsewhere.

Show the decision 
for row in cdc_changes(since=last_watermark):
    cid, text = build_chunk(row)
    h = sha256(text)
    prev = index.get_hash(cid)

    if prev == h:                     # unchanged
        continue
    elif vec := index.find_by_hash(h):
        index.upsert(cid, vec)         # moved: copy, don't re-embed
    else:
        index.upsert(cid, embed(text))  # new or changed

for cid in deleted_ids(since=last_watermark):
    index.hard_delete(cid)             # not a tombstone

Tier 5 · Two classes of source, and the line between them

The dashed arrow is the design. Volatile and personal data skips the pipeline and the index entirely and is fetched live, at request time, by a tool call.

SourcePathFreshness
Course catalogueembeddednightly, or on a change event
Regulations, Studienpläneembeddedweekly — changes rarely, matters hugely
Research outputs, staff expertiseembeddedweekly
Student profiles, transcriptcalled livereal time — never embedded
Timetables, enrolment, deadlinescalled livereal time — never embedded
Two reasons, and the second is the one people miss
  • It would be wrong. A timetable embedded this morning is stale this afternoon, and a vector index has no concept of “this fact expired”.
  • Permissions. A live call inherits the source system's existing access control. Embedding the same data forces that permission model to be rebuilt inside a vector store and kept in agreement forever — which is exactly where student-data leaks come from.

Student profiles sit across the line — personal and volatile. They are called, not embedded: the safer side of an ambiguous case.

The platform box is drawn as provided, not built. The design assumes the university gives access to it. A self-managed lakehouse is a 3–6 engineer, six-month project and is not this role's job — what I own is everything above that line.

Stage 1 · Any client

A student asks from whatever app they already use. No new destination to learn.

  • The layer ships an API and an embeddable widget
  • Identity comes from existing university SSO — no second login
  • Future clients, the staff tier and the public tier all consume the same contract

A new AI portal. It competes with the LMS students already live in, and adoption is the hardest part of any university tool.

Stage 2 · Capability API

Five verbs — ask, find, plan, recommend, assess. Apps compose capabilities instead of each rebuilding a stack.

  • Apps never touch retrieval, models or prompts
  • Improving retrieval improves every app at once
  • OpenAPI for apps, MCP for agents — two front doors, one capability

This is the modular seam this design is built around. A new app is a client, not a project.

Stage 3 · Policy gate

Most designs scrub PII on the way out. This one decides what may be reached on the way in — a librarian checking your ID before the assistant fetches the books.

Three questions, answered before anything is fetched
  • Identity — who is asking, from university SSO
  • Purpose — what this capability may do with that identity
  • Classification — which data classes are in play at all

PII detection as the boundary. The best open detectors reach roughly 0.54 F1 and German is barely tested. Detection is useful defence in depth; it cannot be the control.

A detector that misses a third of what it looks for is indefensible as a gate. Access control can be the gate. Scrubbing still runs — before logging, and before any external call.

Stage 5 · Retrieval

Hybrid, because students type course codes and German compounds, not just concepts.

dense
meaning — “courses about machine ethics”
sparse
exact tokens — INF.02.014
fuse
reciprocal rank fusion, k=60
rerank
cross-encoder, top-50 → top-8

Dense vectors alone. They fail on exactly what a student is most confident typing — and that is the least forgivable place to fail.

Open risk: whether the BM25 extension decompounds German. If Lehrveranstaltungsanmeldung does not match Anmeldung, half the corpus quietly degrades. Load-bearing, and the one thing I could not verify from outside.

Stage 6 · Tools

Don't ask the model to guess a student's record. Give it tools that can check.

What is a tool call, never a generation
  • Remaining ECTS and credit arithmetic
  • Prerequisite satisfaction
  • Timetable conflicts and room bookings
  • Graduation eligibility
Why this beats hallucination detection

It removes an entire class of confident wrong answers by construction, rather than catching them afterwards. A student told they have 12 credits left when they have 24 has been harmed regardless of how good the eval harness is.

Embedding the timetable. An embedded timetable is wrong within hours — which is precisely how California's community colleges gave students wrong financial-aid hours from a stale answer library.

Each tool is an MCP server with a typed schema. Adding the library system, or replacing the SIS, means registering a tool — not modifying the agent.

Stage 7 · Model

You don't send a Ferrari to deliver pizza. Route by task, cost and residency — most student traffic never needs a frontier model.

The constraint that actually decides it

Student data is personal data processed under a public-task basis, so EU-resident inference is a requirement, not a preference. That narrows the field before any benchmark does.

US hyperscalers remain subject to the CLOUD Act wherever the servers sit. Whether that disqualifies them is a governance decision, not an engineering one — my job is to make sure the question gets asked.

Everything speaks one OpenAI-compatible gateway, so swapping providers is a config change. The moat is the context layer, not the model.

Stage 8 · Cite, or refuse

Every claim is checked against what was retrieved before the answer leaves. An honest ‘I don't know’ is a feature.

every call
cheap entailment check — well under a second
~2% sample
LLM-as-judge with claim decomposition — tens of seconds
pre-merge
golden-set regression, blocks the pull request
Why not judge everything

A purpose-built entailment model runs in ~0.6s and costs nothing per call. An LLM judge on the same check takes ~35s and costs per token. Cheap gate on all traffic, expensive judge on a sample — because a check you can only afford sometimes means most answers go unchecked.

When evidence is missing the system says so and points to a human advisor. A refusal is logged as a retrieval failure to investigate, not as a successful safety event.

The ordering rule

Ship in order of what you can check. Find and plan are verifiable by the student in one click, and low harm if imperfect. Paths and competencies are where a wrong answer changes what a student does with a year of their life.

Route by task, cost and residency

You don't send a Ferrari to deliver pizza. Most student traffic never needs a frontier model — and the constraint that actually decides the shortlist is not the leaderboard.

The constraint that decides it

Student data is personal data processed under a public-task basis, so EU-resident inference is a requirement, not a preference. That narrows the field before any benchmark does.

US hyperscalers remain within CLOUD Act reach wherever the servers sit. Whether that disqualifies them is a governance decision, not an engineering one — the job is to make sure the question gets asked.

Licence check, not an afterthought: several of the strongest embedding and reranking models are CC-BY-NC, which a public university service cannot cleanly claim. Apache-2.0 or MIT only — a real constraint that eliminated the top scorer.

Everything speaks one OpenAI-compatible gateway, so swapping providers is a config change. The moat is the context layer, not the model.

Knowing when deterministic software beats a model is part of the answer. Proposing an LLM to detect a timetable clash would be a worse solution, not a more impressive one.

What the model is not allowed to do
  • Compute remaining ECTS or check a prerequisite
  • Decide eligibility, or whether two courses clash

LangChain. Its abstraction depth exceeds what this system needs and debugging through it costs more than it saves at this scale. Haystack or LlamaIndex would both work — if the team already knows one, that beats my preference.

The only genuine agent in the system is learning-path synthesis. Code decides eligibility, prerequisites, credit maths and clashes; the model decides ordering, framing and explanation. It can propose a bad-but-legal path; it cannot propose an impossible one.

Embedded — slow-moving, semantically rich

Content that stays true for a semester, and that people search by meaning rather than by identifier.

Chunking, specifically
  • Course data is already structured, so chunk on the record boundary, not on token count
  • Each chunk carries a deterministic header — programme, semester, course code
  • That header is contextual retrieval at zero LLM cost: the context is metadata we already hold
  • Unstructured policy splits on heading boundaries with the parent section prepended

Semantic / LLM-based chunking. Published comparisons put it roughly 1.6 points ahead of fixed-size while taking hours instead of seconds. For structured records it solves a problem we do not have.

Called live — volatile and permission-sensitive

Two reasons, and the second is the one people miss.

1 · It would be wrong

A timetable embedded this morning is stale this afternoon. Vector indexes have no concept of “this fact expired”.

2 · Permissions

A live API call inherits the source system's existing access control. Embedding the same data forces you to rebuild that permission model inside a vector store and keep the two in agreement forever — which is exactly where student-data leaks come from.

The documented failure: California's community colleges spent millions on student-facing assistants that named a president who had left a year earlier, gave wrong financial-aid hours, and gave an international student guidance that could have affected their visa status. Root cause was a manually maintained answer library that went stale — not the model.

The ambiguous case

Student profiles sit across the line — personal and volatile. So they are called, not embedded: the safer side of an ambiguous case.

Lakehouse → AI-serving layer

Re-embed only what moved. A nightly run that re-embeds the whole catalogue costs real money; one that re-embeds the diff costs almost nothing.

The one thing that forces a full rebuild

Changing the embedding model. So indexes are versioned and swapped blue-green: build the new one alongside, verify against the golden set, switch the read pointer. Never migrate in place; never mix vectors from two models in one index.

Every chunk carries as_of, model_version and a pipeline version. A source that misses its freshness SLA raises an alert, and answers drawn from stale chunks say so.

Show the re-embed decision 
for row in cdc_changes(since=last_watermark):
    cid, text = build_chunk(row)
    h = sha256(text)
    prev = index.get_hash(cid)

    if prev == h:                     # unchanged
        continue
    elif vec := index.find_by_hash(h):
        index.upsert(cid, vec)         # moved: copy, don't re-embed
    else:
        index.upsert(cid, embed(text))  # new or changed

for cid in deleted_ids(since=last_watermark):
    index.hard_delete(cid)             # not a tombstone

Hybrid, because students ask lexical questions

Dense vectors fail on exactly what a student types with most confidence: a course code, a module number, a German compound.

QueryDenseSparseHybrid
INF.02.014 exact code✗ blurs to neighbours✓✓

Lehrveranstaltungsanmeldung~ partial~ needs decompounding✓ with tokenizer
“Prof. Lindstaedt's group”~✓✓
Why rank fusion, not score fusion

BM25 scores are unbounded; cosine similarity is bounded. Fusing raw scores needs normalisation that shifts with every query. Reciprocal rank fusion sidesteps the scale problem entirely and needs no tuning — k=60 is the standard default.

Why 50 → 8 and not 200 → 20

Rerank cost is linear in candidates and the context budget is finite. Beyond ~8 passages the model's attention spreads thin and grounding gets worse, not better.

Measured expectation: published hybrid-vs-single comparisons show roughly a 7% NDCG lift — modest on average. The value isn't the average; it is eliminating a whole category of total failure on lexical queries.

Show the query 
WITH allowed AS (
  SELECT chunk_id FROM chunks
  WHERE visibility = 'public'
     OR (scope = 'user'    AND subject_id = $subject)
     OR (scope = 'program' AND entity_ids && $my_programmes)
     OR  scope IN ('university','global')
),
dense AS (
  SELECT chunk_id, row_number() OVER (ORDER BY embedding <=> $qvec) AS r
  FROM chunks WHERE chunk_id IN (SELECT chunk_id FROM allowed)
  ORDER BY embedding <=> $qvec LIMIT 50
),
sparse AS (
  SELECT chunk_id, row_number() OVER (ORDER BY score DESC) AS r
  FROM chunks WHERE content @@@ $qtext
    AND chunk_id IN (SELECT chunk_id FROM allowed)
  ORDER BY score DESC LIMIT 50
)
SELECT c.chunk_id, c.content, c.as_of,
       COALESCE(1.0/(60 + d.r), 0) + COALESCE(1.0/(60 + s.r), 0) AS rrf
FROM chunks c
LEFT JOIN dense d  USING (chunk_id)
LEFT JOIN sparse s USING (chunk_id)
WHERE d.r IS NOT NULL OR s.r IS NOT NULL
ORDER BY rrf DESC LIMIT 50;

Permissions live on the chunk

Access control is a WHERE clause in the retrieval query — not a filter applied to results afterwards.

Post-filtering is the bug that leaks. If restricted rows are retrieved and then removed, they have already entered the process, the logs, and sometimes the prompt. Pre-filtering means they were never selected.

Why this needs one database

The permission predicate joins against enrolment and programme membership. In a separate vector store those joins become application-side fan-out — slower, and far easier to get subtly wrong. This is the single strongest argument for staying in Postgres at this scale.

The objection this invites

Pre-filtering is the known weak spot of approximate vector indexes. With HNSW the filter is applied after the index scan, so a restrictive predicate can return fewer than k rows, or push the planner into a sequential scan. It is a fair challenge and it has three answers, in order.

  • The filter is not selective in the common case. Course descriptions, regulations and research outputs are university and global scope — visible to every student. The predicate only becomes selective for scope = 'user', which is a small slice with its own partial index.
  • pgvector 0.8 added iterative index scans for exactly this. hnsw.iterative_scan = relaxed_order keeps scanning further into the graph until enough rows survive the filter, bounded by hnsw.max_scan_tuples (20,000 by default). Recall is recovered without abandoning the index.
  • Raising ef_search buys the same thing more bluntly, at a latency cost — the lever to reach for while measuring, not the one to ship.

What this is not: a RAM problem. An index that fits in memory still loses recall to a post-applied filter. Conflating the two is the wrong defence — the fix is iterative scan and index shape, not machine size.

Reversal condition, stated plainly: if filtered recall still degrades measurably after iterative scans and a partial index, Qdrant's filterable HNSW is genuinely better at this and that is the documented point to move.

Remove the error class, don't catch it

The strongest thing I can do about hallucination isn't detection. It's making sure the model never computes the number in the first place.

Deterministic, always

What blocks, and what alerts

  • Refusal rate > 15% in production → retrieval is failing, investigate

Show the gate, and the honest limits of judges 
# gate, simplified
claims = decompose(answer)               # cheap, rule-based
scores = [entail(c, retrieved) for c in claims]

if min(scores) < 0.7:
    return refusal(reason="insufficient_evidence",
                   guidance="Ask your programme advisor")
return answer_with_citations(answer, retrieved)

Judges agree with humans above 80% on well-structured tasks — and still exceed 50% error on adversarial bias benchmarks. They are a useful instrument with known, measured distortions.

BiasMitigation
Position — favours the first optionswap order, average both runs
Verbosity — favours longer answersrubric anchoring with length-matched examples
Self-preference — favours its own familynever let the generating model judge itself
Drift — provider silently updatespin versions; re-baseline on the golden set

Practical rule: if judge-versus-human divergence exceeds 20–25% on a domain spot-check, recalibrate the rubric before trusting any number it produces.

Why scrubbing cannot be the boundary

A detector that misses a third of what it looks for is useful defence in depth and indefensible as a control.

A 2026 benchmark of open PII detectors puts the best average F1 at roughly 0.54 — and German was not among the languages tested.

What is used instead
  • The permission decision happens at the context resolver
  • A scope this person may not reach is never retrieved — so there is nothing to scrub
  • Scrubbing still runs before logging and before any external call — as a second line, not the first

A scrubber at the gateway, calling the privacy problem solved. That design relies on a component that does not work well enough to rely on.

What I would do in a deployment: build a German evaluation set early. Public benchmarks do not transfer, and the honest number for this corpus is currently unknown.

GDPR and the AI Act, asked early

Public authorities cannot rely on legitimate interest for processing carried out in performance of their tasks. So it's public task for the record, and opt-in consent for the AI layer.

substrate
Art. 6(1)(e) public task — the academic record itself
AI layer
opt-in consent — genuinely optional, freely withdrawable

Consent under authority imbalance is fragile — but it works precisely where the service is voluntary and refusing costs the student nothing. Keeping the AI layer separable is what makes the consent real rather than theatre.

Erasure — the architectural decision

Keep all personal data in the retrievable layer, never in model weights. Do not fine-tune on student data. Deleting a row and its vector is ordinary database work with a testable SLA; deleting a person from a fine-tuned model is an unsettled legal question. This converts an open legal risk into a solved engineering task.

Treat embeddings of student text as personal data — inversion research keeps demonstrating that source text can be reconstructed from dense vectors.

AI Act
  • Annex III(3) covers systems that evaluate learning outcomes, including where those outcomes steer the learning process
  • Learning paths and competency tracking plausibly land inside that
  • The Digital Omnibus moved those obligations to 2 December 2027 — that is the window to decide in, not relief
  • No profiling of natural persons — profiling is always high-risk regardless of exemptions
  • Student-facing before staff-facing: a flag to staff becomes a decision under Article 22
What high-risk actually obliges

Annex III classification is not the obligation — it is the trigger for Chapter III, Section 2. Seven articles, and each one is an engineering requirement rather than a paperwork exercise.

Instrumenting in Phase 0 is what makes that a configuration value instead of a retrofit — and it is why the audit trail is built before any student sees a feature.

The distinction that decides how heavy this gets

Building this in-house makes the university the provider, not merely the deployer. Provider obligations are the heavy set — Chapter III Section 2 in full, plus conformity assessment. Buying a system and operating it would land under Article 26 instead, which is far lighter. Which of the two the institution intends to be is a decision to take deliberately, in week one — not to discover in year two.

And if learning paths are wanted on day one

The architecture already survives that. Deterministic tools construct the path — eligibility, prerequisites, credit arithmetic, clashes — and the model only explains a path that has already been validated. Advisory, overridable, no profiling of natural persons.

What day-one shipping cannot skip is Art. 12 logging and Art. 14 oversight. Those are precisely what Phase 0 builds, which is why the sequencing survives the request rather than blocking it.

A DPIA is mandatory — Austria's blacklist triggers on AI, on profiling, and on scoring with adverse effect; any one alone is enough. Budget it into the roadmap. And this is my reading of the statutory structure, not a cited regulator position — it needs counsel, which is itself the point.

Two other things I would check in week one
Is Academic AI already available to the university?

The University of Vienna runs student-facing generative AI on an Austrian cooperative with around 32 participating universities, at roughly €20 per user per month. If generic chat is already purchasable, the entire engineering budget belongs to the context layer — and this proposal gets cheaper and faster. That would strengthen the design, not weaken it: the model was never the moat.

Does the BM25 extension decompound German?

If Anmeldung does not match Lehrveranstaltungsanmeldung, sparse retrieval quietly underperforms across half the corpus. Quietly is the dangerous word — nothing errors, recall just drops.

Closing it takes an afternoon: index 500 real course and regulation records, run 30 compound queries a student would actually type, compare recall with and without the tokenizer.

The mature fallback is Lucene's hyphenation-based compound filter — hyphenate with an FOP pattern file, keep only fragments a German dictionary recognises, then stem both the whole word and the parts. The public german-decompounder data set ships exactly that, and it is what Elasticsearch and Solr use. A general German NLP tokenizer does not solve this: spaCy and SoMaJo segment and lemmatise, neither splits compounds.

The one idea, again

A scope is a permission boundary and a personalization boundary at the same time.

What follows from it
  • Permission before retrieval — denied data is never fetched, so there is nothing to scrub
  • Personalization is the same code path — no second system to keep in agreement
  • Reuse for staff and public is free — a different scope set, not a different build
  • Erasure stays tractable — every chunk carries a subject, so deletion is a filter away

The test for year three: can a new person change the embedding model, or add one tool, in their first week — without reading the whole codebase and without a release freeze?
